# Мониторинг задержки ответа сайтов (7 дней)

Раз в 10 минут замеряет время ответа и код ответа страниц из `targets.csv`,
пишет строку в `data/measurements.csv`. После недели `analyze.py` строит сводку
по часам и дням недели (время московское) и HTML-отчёт с графиками.

Нужен только Python 3.9+; сторонние библиотеки не нужны.

## Что измеряется и чего нет

- `ttfb_ms` — время от отправки запроса до первого байта ответа; ближе всего к нагрузке на сервер.
  `total_ms` — полное время (соединение, TLS, загрузка, редиректы). Также пишутся `dns_ms`,
  `connect_ms`, `tls_ms`, код ответа, число редиректов, размер, ошибка.
- **Это не посещаемость.** Задержка лишь косвенно отражает загрузку: кэш и запас мощности
  сглаживают пики. Вывод вида «ночью задержка ниже на N %» корректен, вывод «ночью
  на сайте N посетителей» — нет.
- **Точка замера важна.** Запуск вне России добавляет международный канал и его колебания.
  Для выводов о загрузке запускайте на сервере в РФ (лучше в Москве) и указывайте `--probe-id`.
- За одну неделю на каждую ячейку «день × час» приходится 6 замеров. Различия между
  соседними ночными часами в пределах 10–20 % — обычно шум, а не закономерность.

## Этика и правила

- Один GET-запрос на адрес раз в 10 минут (≈1000 запросов на адрес за неделю).
  Не уменьшайте интервал: частые запросы могут быть восприняты как атака на сайт.
- Скрипт читает `robots.txt` (раз в сутки, с кэшем) и не запрашивает запрещённые адреса.
- Только общедоступные страницы, без логина, без обхода защиты, без парсинга содержимого.
- User-Agent честно называет скрипт; при желании добавьте контакт: `--user-agent "... (+mail@example.org)"`.

## Запуск на сервере (cron)

```bash
git clone <репозиторий> && cd <репозиторий>/site-load-monitor
python3 probe.py --probe-id msk-vps          # пробный замер, вывод в консоль
date -d '+7 days' '+%Y-%m-%dT%H:%M'          # дата окончания, подставить в --until
crontab -e
```

Строка для crontab (путь и дату замените):

```
*/10 * * * * cd /path/to/site-load-monitor && /usr/bin/python3 probe.py --probe-id msk-vps --until 2026-11-01T12:00 >> data/cron.log 2>&1
```

После `--until` скрипт перестаёт делать замеры; строку из crontab затем удалите.

## Запуск без cron

```bash
nohup python3 probe.py --loop --interval 10m --duration 7d --probe-id msk-vps > data/loop.log 2>&1 &
```

Компьютер должен работать всю неделю без сна и перезагрузок; cron надёжнее.

## Запуск в облачной сессии Claude Code

Сетевая политика окружения должна разрешать `www.consultant.ru`, `www.garant.ru`,
`base.garant.ru` (настройки окружения → Network access → Allowed domains).
Облачный контейнер временный и не работает неделю непрерывно, поэтому годится только для
пробного замера. Точка замера — за рубежом; в отчёте помечайте `--probe-id cloud`.

## Анализ

```bash
python3 analyze.py data/measurements.csv --out report            # по TTFB
python3 analyze.py data/measurements.csv --out report --metric total_ms
```

Результат:
- `report/report.html` — тепловая карта «день недели × час», график по часам (медиана и p90),
  таблица по дням, окна минимальной и максимальной задержки (`--window 3` — длина окна в часах);
- `report/summary_weekday_hour.csv` — та же сводка таблицей (n, ошибки, медиана, p90, мин, макс).

Неуспешные замеры (ошибка сети, код ≥ 400) в расчёт задержки не входят, но учитываются в доле ошибок.

## Адреса

`targets.csv`: `имя,URL`. Главная страница обычно отдаётся из кэша и слабо реагирует на нагрузку;
полезно добавить страницу открытого документа или поиска (проверив `robots.txt`).
Данные в `data/` и `report/` в git не попадают (`.gitignore`).
